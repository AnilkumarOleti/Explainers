Parquet

A Parquet file is a table saved column by column instead of row by row. That one choice makes it several times smaller and much quicker to answer questions from.

Lay the same 30 values

The format shares its name with the wood-block floor. Picture every value in a table as one block. The file format decides how the blocks are laid.

One table, two ways to lay it

A file is one long line, so a table has to be flattened to fit in it. You can go across the rows, or down the columns.

Reason 1 of 3

It reads only what the question needs

Most questions are about one or two columns. When each column sits together, the reader goes straight to those and leaves the rest alone.

Reason 2 of 3

Alike things pack small

A column holds one kind of thing, and it repeats. Parquet writes down each repeat once.

11 MB → 6 KB

The date column of a million orders, as text and then in Parquet. The orders were saved in date order, so each day shrank to one entry: the date, and how many times it repeats.

Row files get little of this, because each value sits next to a different kind of thing: an order number, then a date, then a country. After these tricks Parquet also runs a general-purpose squeeze, like zipping, on every column.

Reason 3 of 3

It keeps notes, so it can skip

Parquet saves rows in chunks. At the very end of the file it writes notes, including the smallest and largest value in every chunk. A reader checks the notes first.

Skipping depends on order. These orders were saved by date. Shuffled, every chunk would span the whole year and none could be skipped.

The real names. Parquet calls a chunk a row group and the notes the footer. PAR1 is the four-letter mark at both ends of every Parquet file.

A million orders, saved three ways

Parquet came out 5 times smaller than the CSV and answered 5 times faster.

How this was measured. 1,000,000 made-up orders with 8 columns, sorted by date. Written and read with PyArrow 25.0.1 on a 2-CPU cloud machine. Parquet used its default settings (Snappy compression) and 10 chunks of 100,000 rows. A stronger setting (Zstandard) brings the Parquet file down to 7.9 MB. Times will differ on other machines and other data; the gap is the point.

Where it is the wrong pick

  • Changing one row at a time

    A Parquet file is written once. To change a single value, the file is written again.

  • Fetching one whole row

    One order is spread across every column. A database finds it faster.

  • Reading it with your own eyes

    The file is packed, not text. A notepad shows gibberish, so you need a tool to open it.

  • Small tables

    A few thousand rows are quick in any format. A CSV is simpler.
